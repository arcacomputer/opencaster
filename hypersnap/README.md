# Opencaster — powered by Arca Computer

An open source client for everyone. Powered by Arca Computer. Runs on Hypersnap. This standalone browser entry offers public browsing and wallet-approved device signing without requiring Quorum messenger registration. Quorum's original messenger source, license, fonts, symbol, and theme tokens are preserved in the parent fork. The new web primitives and shell use its semantic tokens; Farcaster wire signing modules are adapted from the MIT-licensed `quorum-shared` source.

## Run

Use Node 22 and Yarn 1.22. `yarn install --frozen-lockfile`, then `yarn dev`. Vite prints the local URL and proxies `/api` to the public development default; the production Worker can use the optional [private origin](PRIVATE_ORIGIN.md). `yarn verify` runs the protocol/API/Worker tests and typechecks both browser and Worker code before the production build.

`yarn verify` also typechecks and bundles the offline companion. The parent repository's separate verification belongs to the retained Quorum messenger and needs its linked sibling repositories and dependencies. Never bypass its bot mint guard.

## Deploy

Follow the [release checklist](#release-notes), including the dev log check, verification and a build in a fresh external directory. `wrangler.jsonc` targets the Arca Cloudflare account, the `hypersnap-quorum` Worker, and the `opencaster.org` custom domain and the old domain redirect. Use your own account/domain when deploying another fork. Authentication is handled by the local Wrangler CLI; credentials never belong in source or browser environment variables.

Copy `.env.example` to your own ignored `.env.local` for local development, or provide `VITE_WALLETCONNECT_PROJECT_ID` in your build environment for wallet app connections. Obtain your own public project ID from the [Reown Dashboard](https://dashboard.reown.com). Allowlist the precise deployed origins in its project configuration. No Dashboard API secret, private wallet key, social login, or hosted account authentication is needed. Vite embeds this public ID into the browser bundle; changes require a rebuild. Missing configuration disables WalletConnect while browser wallet and offline approval remain available.

The Worker serves static assets and adds CSP, no-referrer, no-store HTML, and other browser security headers. API routes use a configured server-only primary, an explicit route/query allowlist, response size/time bounds, and signed binary submissions limited to 64 KiB. Production configuration selects the private `https://node.opencaster.org` origin and an explicit, fixed Haatz read backup; incomplete private configuration fails closed. Fork/development configurations with both private settings absent retain the public Haatz default. Eligible reads prefer primary and make at most one backup attempt after transport failure, timeout or HTTP 5xx, within one 20-second deadline. Signed submissions are never replayed automatically, media signer checks remain primary-only, and the origin credential never goes to the backup. `X-Opencaster-Upstream` identifies the selected backend without exposing credentials. See [PRIVATE_ORIGIN.md](PRIVATE_ORIGIN.md) for the complete contract and bounded public-aggregate cache. The current private origin deliberately returns 503 for unready `/v2/` projections, so Haatz serves those reads rather than stale feed/profile data; this does not claim that the private indexes are complete.

The gateway forwards neither browser cookies nor authorization headers, follows no redirects, and emits no custom application request logs. Cloudflare persists platform invocation logs with request metadata and redacted query strings; automatic traces remain disabled. First-party aggregate usage and request-health measurements use the separate Cloudflare Analytics Engine dataset; see [OBSERVABILITY.md](OBSERVABILITY.md) for dashboard links, coverage, schema and visitor opt-out. A separate operator dashboard is configured in `wrangler.analytics.jsonc` for `analytics.opencaster.org`, with Cloudflare Access and Worker-side Access application verification before any analytics query. It requires its own Access application, exact-email policy and deployment; missing authentication configuration denies access. The private local HTML report remains available through `yarn analytics:report`. Public images use a dedicated R2 bucket; a SQLite-backed Durable Object enforces upload nonces and daily quotas. Deploy the R2/DO bindings and migration declared in `wrangler.jsonc`; see [MEDIA.md](MEDIA.md) for provisioning, retention, and limits. Both nodes remain availability dependencies; the gateway is not an independent indexer. Apply appropriate account-level abuse/rate controls before scaling traffic.

## Signing model

Sign-in has its own `/connect` page. Enter a public username, ENS/Base name, FID or exact custody wallet address to look up the same complete account summary: canonical username (or an honest unavailable label), FID and full custody address. Lookup does not request a wallet signature or generate a device key. **Use this account** prepares a fresh request for the reviewed FID; if its username or custody address changed, the new identity must be reviewed before wallet approval becomes available. Account identifiers and requested permissions are never taken from the sign-in URL. Back/cancel discards the pending attempt, and reload starts with the default permissions. Returning users can unlock an explicitly saved encrypted key on the same page.

ENS lookup uses Hypersnap's indexed name proofs through the fixed gateway's `/v1/fidByName` route, then hydrates that exact FID. Both `name.eth` and `name.base.eth` are supported, including mixed-case input and an optional leading `@`. Current Hypersnap rules limit the name label to 1–16 ASCII letters, digits or hyphens, starting with a letter or digit. Unicode names, other suffixes and additional subdomains are outside this flow. A name must already be linked to an account in the node's index; owning a name or pointing its Ethereum address record at a wallet does not by itself create that association. This performs no name registration, reverse-name lookup or general Ethereum resolution, and adds no external RPC dependency. The ENS proof owner or resolved wallet can differ from the account's custody wallet; approval still requires the current custody address shown in review. Profile links and exact username lookups use the same native name resolution.

The website never accepts a recovery phrase. It generates a random Ed25519 posting key in the browser and asks a compatible wallet app to approve it using `eth_signTypedData_v4`. Desktop extensions and wallet browsers connect through EIP-1193/EIP-6963. The browser-wallet selector includes announced providers and bounded legacy provider lists and extension namespaces, including Coinbase Wallet and Rainbow, even when another extension owns the default provider. Multiple providers require an explicit choice; names and brands are self-asserted discovery hints, not authentication. Normal Safari/Chrome can also connect a separate wallet app using WalletConnect's encrypted external relay, with a locally generated QR code or explicit mobile wallet links. This optional connection requests typed-data signing only and ends after approval or cancellation; no wallet transaction or Ethereum RPC provider is requested. WalletConnect is an external availability and metadata dependency. No Farcaster-operated login service is involved. The selected wallet must expose the public account's exact custody address. The browser verifies both custody signatures before the user separately submits Hypersnap's gasless KEY_ADD. Login creates no NFT or Ethereum transaction receipt.

If an extension reconnects the wrong account, select the imported Farcaster custody account inside that wallet and review its connected-site controls, then retry here. A different verified wallet cannot substitute for custody. **Cancel wallet approval** releases this site's pending attempt and ignores late responses; it cannot close a wallet's popup, so reject any outstanding prompt before retrying. **Refresh browser wallets** repeats detection without requesting wallet permissions. Compatibility requires recoverable Ethereum-account EIP-712 signatures: smart-contract wallets, non-EVM providers and incompatible signing implementations are not supported by this Hypersnap flow.

Default device keys request `[1, 3, 4]`: casts/replies and adding/removing reactions. Following, unfollowing, and editing a profile require a separate, explicit approval for a new key with `[1, 3, 4, 5, 6, 11]`. The connection page displays these added permissions before signing. The current session remains usable until the new key is confirmed; approving the new key does not revoke the old one. Deleting your own casts requires a further explicit key approval for `[1, 2, 3, 4, 5, 6, 11]`, followed by a separate deletion confirmation. All permission sets use a **seven-day sliding inactivity window**, refreshed by protocol activity, rather than a fixed seven-day expiration. The optional offline **Arca Signer v0.2.0** beta supports only the original casts/reactions permissions; use a compatible wallet for the expanded social permissions.

The app exchanges public account data, signatures, and signed protocol messages; custody private keys and recovery phrases remain in the selected wallet or offline companion. WalletConnect adds encrypted transport traffic and temporary pairing material, so its QR code and pairing link must be treated as secrets. The native app denies network requests and has no phrase persistence, telemetry, remote scripts, or updater. Mutable secret buffers are wiped where possible; JavaScript strings and library internals cannot be guaranteed to be zeroed. The browser keeps its posting key in memory unless the user explicitly saves an encrypted IndexedDB vault. On a compatible browser/passkey provider, a passkey’s WebAuthn PRF output derives a local AES-256-GCM encryption key using HKDF-SHA256. Returning users unlock through their passkey provider’s device verification, such as a fingerprint, face scan, or PIN. The PRF output and encryption key never go to our server. Password-encrypted vaults (PBKDF2-SHA256, 600,000 iterations; AES-256-GCM) remain available and older vaults stay compatible. Passkeys unlock an already authorized app key; the first connection, an expired/revoked key, or expanded permissions still require custody-wallet approval. A passkey provider may sync its credential, but this app’s encrypted vault remains in this browser on this exact site. A new browser/device or cleared site storage requires wallet reconnection. PRF support is checked on the actual credential: unavailable support or cancelled setup never silently saves a plaintext key or replaces an existing vault. Locking clears the active key but preserves the encrypted vault. Forgetting removes the vault; revoking removes the current key from Hypersnap, confirms its absence, then erases its saved copy. Revocation can also use an offline custody approval. See [SIGNER.md](SIGNER.md) for the full trust model and release verification.

For a submission timeout, network inclusion is unknown: inspect the profile or signer state before manually retrying. The app never retries writes automatically. Profile fields are separate signed messages: successful fields are retained after a partial save, and uncertain fields remain blocked until their attempted values appear on the public profile. Uncertain follow changes likewise require a status check. Successful submissions are acknowledged by the node, not independently proven finalized.

The composer uses one expanding text box with compact photo/GIF-file, mention, emoji and draft tools. Exact username/FID lookup, saved-draft recovery and help open only when requested; inline @ suggestions and Cmd/Ctrl+Enter remain available. Emoji insert Unicode locally, and pasted links stay cast text. Draft saves remain explicit, scoped to the account and destination, and stored only in this browser tab for up to 24 hours. No hosted GIF catalog, video processor, poll or scheduling service is connected.

Image uploads use a constrained, short-lived authorization signed by the existing device key, not another wallet approval. The current client allows up to two embeds: images and quoted cast references share that limit. Uploaded images are public and persistent, and their original photo metadata, including EXIF, is retained. A short notice stays visible before upload; Media info explains formats, limits and persistence. Removing an image from a draft does not delete its upload; no end-user media deletion flow is included. See [MEDIA.md](MEDIA.md).

## Scope and verification

The public [dev log](https://opencaster.org/devlog) records the standalone client's history from its first commit. It is available without sign-in, with topic filters, oldest/latest ordering and links to the code behind each milestone. The header link remains available on small screens.

Every feature/fix release must include a new milestone; the [release checklist](#release-notes) and CI enforce that requirement. The page and its styles load only when opened.

### Domain migration

Public links from `quorum.arca.computer` redirect to the same path and query on the new canonical domain. Legacy media URLs retain their content hash and existing R2 bucket. Legacy write requests return `409 site_moved` before reading a body or reaching Hypersnap, so signed bytes are never forwarded across an origin-changing redirect. Reopen the new site and reconnect your existing wallet.

Saved device keys/passkeys and other local browser data are bound to the original origin and cannot transfer automatically. New-domain saving is optional and requires a fresh setup after connection. Protocol signing labels, device scopes, upstream endpoints and existing network authorizations are unchanged. The Worker service name and storage bindings remain stable to preserve media and quota state.

## Release notes

1. Record the commit currently deployed before starting the release. Implement and commit the feature or fix, then prepend a milestone in `src/lib/devLog.ts` before shipping. Its source link uses the implementation commit's full hash and its recorded author date (`git show -s --format=%aI <commit>`). A separate note commit avoids a circular hash. Group related work if useful, but describe every shipped feature or fix.
2. Give the note a unique ID, title, summary, topic and concrete changes. Describe user-visible behavior and relevant limits. Keep plans separate from completed work, preserve earlier milestones, and date verification claims rather than implying continuous coverage.
3. From `hypersnap/`, run `yarn check:devlog --base <currently-deployed-commit>` and `yarn verify`. Without `--head`, the guard includes committed, staged, unstaged and untracked work. For a committed range, add `--head <commit>`; for a feature branch comparison, add `--merge-base`. Fetch the base/history first. Missing history is an error, never an exemption.
4. Build into a **new** directory outside this cloud-synced checkout: `yarn build --outDir /tmp/arca-release-<unique-name>`. Inspect its contents, then use `wrangler deploy --assets /tmp/arca-release-<unique-name>` and confirm the live `/devlog` includes the release. Never deploy preview wrappers or isolated-test fixtures. Record the deployed commit and Worker version with the release verification.

CI runs the guard for PRs and pushes. Default-branch pushes compare the event's before/after commits; PRs and feature-branch pushes compare their merge base with the target/default branch, so incremental branch commits can share a release note. A new default branch with an all-zero previous SHA compares against an empty tree. A runtime, UI/style, public-asset, signer, build/config or dependency change requires a **new ID**; editing an old entry does not satisfy it. Docs, tests, protocol golden fixtures, licenses, the log data itself and development-only E2E/guard scripts are exempt. Unknown files in `hypersnap/` require a note. New entries must link to an existing ancestor implementation commit with its recorded date; the guard also checks literal data, unique IDs, fields, real dates, newest-first ordering and preserved history.

CI validates that an entry exists and its source is real; release review still checks that the prose accurately covers the changes. It does not intercept a direct manual Wrangler command. Contributors and coding agents must run this checklist for every deployment, including hotfixes. See [AGENTS.md](AGENTS.md).

## Link previews

Shared links include Open Graph metadata for Telegram and other link-preview
clients, plus an X large-image card. The initial HTML contains the title,
description, image URL and image alt text; crawlers do not need JavaScript or a
Hypersnap API request. The public 1200×630 PNG introduces Opencaster as an open
source social client for Hypersnap, powered by Arca Computer.

The gateway preserves recognized profile, cast, channel and other page URLs in
the canonical and Open Graph URL fields, using `https://opencaster.org` and only
supported query fields. These links currently share the platform introduction;
they do not generate individual author portraits or cast excerpts. Preview
appearance and refresh timing depend on each sharing app's cache and settings.
The versioned image lives beside its editable SVG in `public/`; use a new image
filename and update both metadata sets when replacing published artwork.
Re-render the PNG from `hypersnap/` with
`rsvg-convert -o public/opencaster-social-v1.png public/opencaster-social-v1.svg`.
The SVG outlines its text and needs no installed fonts.

## Supported behavior

Implemented:

- Automatically loading timelines for Discover, Following, channels and profile tabs, with inline loading/retry feedback and continuation through sparse or locally filtered pages. Scrolling loads the next page near the bottom until Hypersnap returns no continuation; repeated cursors stop safely. Browser history, node availability and indexed-history limits still apply.
- Public trending feeds with 1-hour to 7-day windows and following home tabs, shareable profile Casts/Replies/Photos/Likes/Recasts tabs, indexed channel discovery/search/detail/feeds and channel posting, bookmarks, dark/light theme, responsive navigation, and session locking.
- Search public casts or people at `/search`; shareable queries and profile tabs survive Back/Forward and direct loads. Cast search is a bounded ranked result set; people search uses the node’s prefix index.
- Recent notifications at `/notifications` for follows, reactions, replies and mentions, with All/Unread/type filters and per-account read state stored on this device. Hypersnap’s bounded activity scan is not a complete historical inbox; the client never calls the node’s placeholder mark-seen POST.
- Protocol quote embeds and confirmed deletion of the connected account’s own casts. Unknown deletion submissions permit read-only reconciliation, with no automatic resubmission.
- Shareable cast links at `/<username>/0x<8-hex-prefix>` (or the author FID when a username is unavailable), public profiles at `/profile/<fid>` or `/profile/<username>`, and the connected account's `/profile` page. Root `/<username>` profile links and `/<username-or-fid>/0x<hash-prefix>` cast links also work, including supported ENS/Base identifiers. Browser Back/Forward and direct page loads restore these views; sharing uses our canonical domain and the same author/hash-prefix path shape as Farcaster. Existing `/cast/<full-hash>` links remain supported.
- Timeline replies identify the recipient and preview their parent cast. Conversations show up to eight earlier casts in order above the selected reply, with a 20-second context deadline, earlier-context navigation and retry/unavailable states. Parent previews and earlier casts honor local content controls. Nested replies identify their recipient, with casts/replies and like/recast add/remove. Connected-user reaction state uses actual account-scoped protocol receipts after refresh; unknown reaction writes remain blocked in the active session until their intended state is visible. Existing protocol mentions become clickable profile links using validated UTF-8 insertion positions. The composer resolves a username or FID through Hypersnap and inserts an explicitly selected account mention; ordinary unselected `@text` stays literal.
- Public follower/following lists, following/unfollowing after explicit expanded permission approval, and editing display name, bio, or profile image. Banner writes are excluded because Hypersnap requires Pro status and does not reliably hydrate them in its public user response.
- Explicit account/destination-scoped draft Save/Restore/Discard in this browser tab (24-hour TTL), inline mention suggestions with keyboard selection, Ctrl/Command+Enter publishing, pasted-image uploads, an accessible image viewer, copy-cast-text tools, and profile sharing/linked-address details. Drafts contain only text, public mention references and uploaded image URLs; they never contain signing keys or auto-submit.
- Saved channel shortcuts labeled as browser-local, paginated channel participants (accounts that posted), bounded friends-of-friends profile suggestions, and a bounded quote-cast viewer with explicit node-index limits.
- Per-account and guest browser-local content settings: mute accounts or literal words/phrases, hide casts, undo filters and temporarily reveal a view. Known activity previews and quoted casts honor these controls; opaque quoted text is not inferred. They do not block anyone on the network or sync across devices. Each account’s in-memory preferences remain usable if storage is denied; saved settings and temporary reveals never cross accounts.
- Local bookmark search by text/person/channel, newest/oldest saved order and confirmed clearing, with bounded validated snapshots and legacy migration. Paginated public Likes/Recasts people lists use actual v1 receipts and cap their node-reported view at 1,000 profiles or 40 pages.
- Search shortcuts (Cmd/Ctrl+K or slash), shortcut help (question mark), and safer literal HTTP/HTTPS link punctuation. Navigation shortcuts pause while typing or inside dialogs.
- Authenticated public JPEG, PNG, WebP, or GIF uploads up to 5 MiB, with up to two image attachments per cast. The R2/SQLite Durable Object storage and quota boundary is documented in [MEDIA.md](MEDIA.md).

Excluded: creating Farcaster accounts, paid storage/on-chain registration, seed recovery, wallet transfers, DM transport, push notifications, video uploads, end-user media deletion, and mini-app execution. Channel discovery depends on the Hypersnap node’s channel index. Channel parent URLs are protocol identifiers; the client does not contact any external service to resolve them.

See [FEATURE_SUPPORT.md](FEATURE_SUPPORT.md) for the source-backed feature matrix and upstream limitations.

Cast permalinks and the share dialog use `opencaster.org/<username>/0x<8-hex-prefix>`, matching the author and short hash format in Farcaster links. Known casts open directly within the current tab; newly loaded short links still use the bounded Hypersnap lookup below. Automatically opening a verified short-link match retains that URL, while choosing among multiple returned matches opens an author-scoped full-hash path. If the author has no usable username, the link uses their FID. Legacy `/cast/<full-hash>` URLs remain valid and move to the author-style permalink once the cast is loaded.

For a Farcaster-style cast link, replace its host with `opencaster.org`, keeping `/<author>/0x<hash>` intact. Changing a host cannot restore a cast unavailable from Hypersnap. Hashes may contain 8–40 hexadecimal characters in complete bytes. Full hashes use an exact author/FID lookup. Hypersnap currently has no native short-hash index, so short links search the author's available history in explicit batches of up to four 250-message pages. When a fully checked history page returns one currently available cast verified by its exact author and full hash, the conversation opens immediately and cancels remaining lookup reads. No confirmation click or completed history scan is required. This selects the first available verified match; it does not establish that the prefix is unique throughout the author’s history. If a returned snapshot contains multiple verified matches, choose an exact author/full-hash **Open cast** link. If no match has been found, **Search older casts** checks another bounded batch; an incomplete search never claims absence. Each batch has a 25-second deadline, at most four simultaneous candidate reads, and bounded cumulative history/candidate limits. History includes cast removals; matched adds are hydrated again to confirm current availability. Deleted/pruned casts or data absent from this node cannot be restored by changing a URL. These are public Hypersnap reads; Farcaster client account status is not queried.

Supported HTTPS profile and cast links to `farcaster.xyz` or legacy `warpcast.com` (including their `www` hosts) now open on Opencaster when rendered in cast text, non-image URL attachments or profile bios. Normal clicks use local navigation; modified clicks and copied link targets also point to Opencaster. The original authored text and protocol URLs are preserved. Root profile links, author/hash links and the full-hash `/~/conversations/<hash>` fallback are recognized; tracking query/fragment data is discarded. Other sites and unsupported Farcaster handlers retain their existing external behavior. Recognition uses the original URL token and exact allowed hosts rather than contacting a Farcaster redirect or resolver service.

The [MIT-licensed Farcaster client snapshot](https://github.com/farcasterxyz/client) informed familiar sharing, profile, and conversation UX. These features are independently implemented against Hypersnap; no Farcaster-hosted API client, account service, websocket, or source dependency was imported.

Automated checks use synthetic keys, mocked HTTP responses, and an independent Rust protocol golden vector. The project owner reported a successful real Rainbow browser-extension sign-in. Agent-run production checks perform public reads and navigation only; they do not sign real account actions or publish user media. Follow/profile writes and image-backed casts have not been exercised against a real production account by this development session. See [VERIFICATION.md](VERIFICATION.md) for the current checks and limitations. This is a beta, and no independent security audit is claimed.
