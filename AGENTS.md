# AGENTS.md

This repository is **Opencaster**, an independent open-source social client for
Hypersnap developed by Arca Computer and deployed at **opencaster.org**. Its
applications, supporting services and shared packages use Yarn workspaces under
`apps/`, `services/` and `packages/`.

Opencaster originated as a fork of Quorum Desktop. The earlier messenger source
and development records remain in Git history and the upstream repository; the
current tree contains Opencaster. Preserve upstream attribution, applicable
licenses, and earlier names in historical records. Do not restore the old
messenger or its tooling as a dependency of this client.

## Application boundaries

| Area | Purpose |
| --- | --- |
| `apps/web-client/` | React browser client, local UI entry points, styles, assets and browser harnesses. |
| `apps/signer/` | Optional offline Electron signing companion. |
| `services/gateway/` | Cloudflare gateway, media storage, link previews and request measurements. |
| `services/analytics/` | Operator analytics dashboard and local report tooling. |
| `packages/protocol/` | Shared wire encoding and signing primitives. |
| `packages/client-core/` | Shared API, route, content, pairing and media contracts. |
| `packages/web-ui/` | Browser UI primitives shared by web-client and signer. |
| Root scripts and configs | Workspace orchestration, tests, release checks and dependency lockfile. |

Keep the workspace boundaries and declare each package's direct dependencies.
Shared packages must not import application or service source. Platform-specific
wallet, passkey and vault implementations remain with their client. Historical
Worker and storage names, legacy domain redirects and browser storage identifiers
support existing users; do not rename them as cosmetic cleanup.

## Development and verification

- Use **Yarn exclusively**, Node 22 and Yarn 1.22. Do not run npm commands or
  introduce `package-lock.json`; remove any generated by your work.
- Install from the repository root with `yarn install --frozen-lockfile`.
  Keep the single root `yarn.lock`. Root `yarn dev` starts the web client;
  `yarn test`, `yarn build` and `yarn verify` cover the monorepo. Use
  `yarn workspace @opencaster/<name> <script>` for a specific workspace.
- Keep types, hooks, utilities, and components with the existing local code.
  Use `apps/web-client/src/components/ui.tsx` for Button, Input, and Modal primitives
  (re-exported from `packages/web-ui/src/ui.tsx`) and local SCSS semantic tokens.
  No Quorum sibling checkout or linked
  `@quilibrium/quorum-shared` package is required.
- Follow React's Rules of Hooks: top level, same order on every render, before
  conditional returns.
- Run **`yarn verify` from the repository root** before reporting completion.
  It runs all workspace tests, shared-package/browser/gateway/dashboard
  typechecks, the production browser build and offline signer typecheck/build.
  Verify relevant workspace entry points when changing their scripts or CI.
  Report failures and coverage limits.
- Browser and real-network behavior beyond the gate require separate relevant
  verification. All write tests use synthetic isolated identities. Production
  checks are public reads/navigation unless the user explicitly authorizes a
  real account action. No independent security audit is claimed.

## Releases

These release rules cover all `apps/`, `services/` and `packages/` workspaces,
root dependency/build configuration and shipping build scripts. Follow the
[release checklist](apps/web-client/README.md#release-notes).

- Features, fixes, security/dependency updates, UI changes, gateway changes and
  shipping build/configuration changes require a **new milestone** in
  `apps/web-client/src/lib/devLog.ts`. Docs-only and test-only changes need no
  announcement. Keep existing milestone IDs and recorded implementation links.
- Write for users: state the change, its benefit and relevant limits. Never
  present a plan or unverified capability as shipped. Preserve Hypersnap and
  infrastructure limits; UX similarity does not establish Farcaster service
  compatibility.
- Commit the implementation first, then add the note in a separate commit before
  shipping. Link its full repository commit URL and recorded Git author date;
  this avoids a self-referencing hash. Group related changes if useful, but
  describe every shipped feature/fix.
- Before deployment, record the **actual pre-release deployed commit**. From the
  repository root run `yarn check:devlog --base <pre-release commit>` and
  `yarn verify`. A newly updated `origin/main` is not a substitute for the deployed
  base. The guard preserves dev-log history across the old `hypersnap/` layout
  and the current workspaces. CI checks PRs against their merge base and
  default-branch pushes against the previous SHA.
- Build production browser assets in a fresh external directory using
  `yarn workspace @opencaster/web-client build --outDir /tmp/arca-release-<unique-name>`.
  Inspect those assets, deploy that exact directory with
  `wrangler deploy --config services/gateway/wrangler.jsonc --assets /tmp/arca-release-<unique-name>`,
  and confirm the live `/devlog`. Never deploy a test fixture or preview wrapper.
  The analytics dashboard uses its own `services/analytics/wrangler.jsonc`.
- All write tests use isolated synthetic identities. Production checks are public
  reads/navigation unless the user explicitly authorizes a real account action.

## Secrets and private security records

- Never widen where private keys, keysets, recovery phrases, or ratchet state
  can be observed. No globals, unencrypted persistence, logs, telemetry, or
  crash payloads. Debug diagnostics must be build-gated; inspect built output.
- Keep credentials out of source and browser environment variables. Follow the
  distinction between public build identifiers and secrets.
- `.agents/issues/.secret/` remains gitignored for any locally retained private
  reports, even though the inherited public documentation has been removed.
  Preserve ignored local files during cleanup. Never publish report details or
  titles in tracked files, indexes, commits, or PR descriptions.
- A write-up describing an attack against shipped code, or materially helping
  build one, belongs in that private directory **from the start**. Ordinary
  reliability, data-loss, and correctness issues can be documented publicly
  when they disclose no attack.
- Merging and releasing are separate: completed private reports may move to
  `.agents/issues/.secret/.done/` after merging, still ignored. Only after the
  fix actually reaches users may a deliberate publication move the write-up
  into public documentation. A merged fix alone never authorizes publication.
